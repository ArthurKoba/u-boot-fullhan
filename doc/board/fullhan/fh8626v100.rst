FH8626V100
==========

The FH8626V100 is an ARM1176-based Fullhan camera SoC.  The port supports
64 MiB of SDRAM, the DesignWare APB UART and timer, two DesignWare GPIO
banks, SPI NOR, and the DesignWare Ethernet MAC in RMII mode.  Linux is
started with legacy ATAGs and machine ID 9999, as required by the available
FH8626V100 Linux 4.9 platform code.

Two configurations are provided:

``fh8626v100_flash_defconfig``
    Production configuration linked at ``0xa0800000``.  The Fullhan
    bootstrap loads it from the 192 KiB NOR slot at offset ``0x20000``.
    The environment occupies the preceding 64 KiB sector at ``0x10000``.

``fh8626v100_ram_defconfig``
    Non-persistent development configuration linked at ``0xa3000000``.
    It can be loaded and started by the vendor U-Boot without writing NOR.

OpenIPC boot contract
---------------------

The default environment follows the OpenIPC raw-NOR layout used on the
validated 8 MiB camera:

=================  =====================
NOR range          Purpose
=================  =====================
``0x000000-00ffff`` Fullhan bootstrap
``0x010000-01ffff`` U-Boot environment
``0x020000-04ffff`` U-Boot
``0x050000-34ffff`` Linux legacy uImage
``0x350000-44ffff`` ``rootfs_data``
``0x450000-7fffff`` SquashFS root filesystem
=================  =====================

``openipc_boot`` reads the 3 MiB kernel partition to ``0xa1000000`` and
boots it with the root filesystem on ``/dev/mtdblock5``.  ``netboot`` loads
the same kernel image over TFTP.  The default ``bootm_low=0xa0000000`` and
``bootm_size=0x02700000`` describe the 39 MiB visible to Linux.  OpenIPC can
identify the platform through ``soc=fh8626v100`` and
``manufacturer=fullhan``.  ``bootcmdnor`` selects the flash boot command used
by OpenIPC installation and recovery tools.
SPI NOR uses the standard ``sf`` command and the DesignWare FIFO transfer
path.  Transfers are bounded to the hardware FIFO depth to avoid receive
overruns on this controller.

This platform intentionally does not use Standard Boot.  Its deployed Linux
port requires legacy ATAGs, a fixed machine ID, and a fixed raw-NOR layout.

Build
-----

Use an ARM EABI cross compiler::

    make fh8626v100_flash_defconfig
    make CROSS_COMPILE=arm-linux-gnueabi-

For an OpenIPC-style release build, use ``build.sh``.  The raw open-source
binary and padded U-Boot partition are always written to ``output/``::

    CROSS_COMPILE=arm-linux-gnueabi- ./build.sh

The Boot ROM does not load U-Boot directly.  It interprets a board-specific
64 KiB Fullhan container.  The recovered header, descriptors, DDR parameter
records and legacy data are represented by the auditable
``board/fullhan/fh8626v100/bootrom.json`` manifest.  ``build.sh`` generates the
container and the standard OpenIPC NOR asset without a vendor binary blob.
This representation is a byte-exact reproduction of the working original; it
is not a complete semantic reverse engineering of the mask-ROM interpreter or
every container field.  The generated boot chain has successfully started
U-Boot and loaded the installed firmware on the target camera.

A verified 8 MiB stock dump can optionally replace the manifest as an
independent recovery and validation input::

    FH8626_FLASH_BACKUP=/path/to/stock-8m.bin \
      CROSS_COMPILE=arm-linux-gnueabi- ./build.sh

The recovered container format and the confidence level of every known field
are documented in :doc:`fh8626v100-boot-format`.

The outputs are:

``u-boot-fh8626v100.bin``
    Raw U-Boot binary.

``u-boot-fh8626v100-bootstrap.bin``
    64 KiB generated Boot ROM container for the permanent fixed-envelope
    U-Boot contract.

``u-boot-fh8626v100-partition.bin``
    192 KiB padded U-Boot partition for an environment-preserving update.  It
    is generated without requiring a bootstrap dump.

``u-boot-fh8626v100-nor.bin``
    320 KiB OpenIPC boot region.  Its environment sector is erased so the
    compiled defaults are used.  Flashing this file replaces the existing
    environment.

``SHA256SUMS``
    Checksums for every generated binary.

Atomic boot-chain update
------------------------

The vendor bootstrap describes the vendor U-Boot's build-specific size and
JAMCRC.  It cannot load an arbitrary replacement.  This port instead uses a
permanent ROM-visible contract: raw size ``0x30000``, aligned size
``0x30000`` and JAMCRC ``0x251d4c31``.  The packer fills the unused partition
tail and calculates a four-byte correction at its end, so different U-Boot
builds retain the same geometry and checksum.

Keep a verified full-flash backup and a separate copy of the installed U-Boot
partition before any persistent update.  After the RAM target and the flash
binary have passed their non-persistent tests, program the pair in this order:

#. erase, write, read back and compare the fixed-envelope U-Boot partition at
   ``0x20000``;
#. without resetting, erase, write, read back and compare the generated
   permanent bootstrap at ``0x00000``;
#. reset only after both comparisons pass.

This paired procedure is required exactly once when migrating from the vendor
bootstrap.  After a successful cold boot through the permanent bootstrap,
later U-Boot releases update only the partition at ``0x20000``; rewriting the
bootstrap is neither necessary nor recommended.

An interactive migration from the vendor U-Boot uses separate buffers and
keeps the environment sector untouched.  Confirm that TFTP reports exactly
``0x30000`` and ``0x10000`` bytes before the first erase::

    sf probe 0:0 50000000
    tftpboot 0xa1000000 u-boot-fh8626v100-partition.bin
    tftpboot 0xa1040000 u-boot-fh8626v100-bootstrap.bin
    sf erase 0x20000 0x30000
    sf write 0xa1000000 0x20000 0x30000
    sf read 0xa1080000 0x20000 0x30000
    cmp.b 0xa1000000 0xa1080000 0x30000
    sf erase 0x00000 0x10000
    sf write 0xa1040000 0x00000 0x10000
    sf read 0xa10c0000 0x00000 0x10000
    cmp.b 0xa1040000 0xa10c0000 0x10000

Both ``cmp.b`` commands must report every byte equal before ``reset``.  For a
later fixed-envelope release, repeat only the ``0x20000`` partition write and
comparison; do not rewrite offset ``0x00000``.

Do not erase or write the environment sector at ``0x10000`` during an
environment-preserving update.  ``u-boot-fh8626v100-nor.bin`` includes an
erased environment sector and is intended only when resetting the environment
is deliberate.  If power is lost during the one-time migration, or the board
is reset with a vendor/fixed-envelope mismatch, U-Boot cannot provide
recovery; restore the previous matched pair or write the permanent bootstrap
with an external SPI-NOR programmer.

RAM validation
--------------

Place the RAM build in the TFTP root and run the following from the vendor
U-Boot::

    setenv autostart no
    tftpboot 0xa3000000 u-boot-fh8626v100-mainline-ram.bin
    crc32 0xa3000000 ${filesize}
    go 0xa3000000

Power cycling returns to the installed boot path.  Do not issue ``sf erase``
or ``sf write`` during initial RAM validation.  Useful read-only checks are::

    gpio status -a
    sf probe 0:0 50000000
    sf read ${loadaddr} 0x50000 0x300000
    iminfo ${loadaddr}
    mii device
    ping ${serverip}

Environment migration
---------------------

The vendor U-Boot GPIO command syntax is incompatible with current U-Boot.
When preserving a vendor environment, update only the boot-critical fields
and retain board calibration variables such as motor ranges and lens data::

    setenv ethact
    setenv set_gpio 'gpio set 23; gpio clear 0; gpio clear 1; gpio clear 2; gpio clear 3; gpio clear 7; gpio clear 6; gpio clear 50; gpio clear 51; gpio clear 18; gpio clear 60'
    setenv bootcmd 'run openipc_boot'

Test the resulting boot before using ``saveenv``.

Hardware validation
-------------------

The flash configuration has been validated on an ANJIA AJL33PQ0866 camera:

* cold boot through the Fullhan ROM and bootstrap;
* persistent environment read from SPI NOR;
* two matching 3 MiB NOR reads at 50 MHz and valid legacy-image CRC through
  the bounded FIFO path;
* RMII PHY ID ``0x937c4024``, 100 Mbit/s full duplex, ping and TFTP;
* GPIO banks 0 and 1 and the board output initialization sequence;
* Linux 4.9 flash-root boot through the OpenIPC login prompt.

A release image must pass the repeated-read and CRC gate after a cold boot.
RAM-chainload success alone is insufficient because it can inherit earlier
hardware initialization.

The fixed-envelope packer is machine-tested, but the one-time migration to its
permanent bootstrap still requires cold-boot hardware validation.  Until that
test passes, it is a release candidate rather than a hardware-proven updater.
